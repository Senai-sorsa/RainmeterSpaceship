A4. RULES THAT ALWAYS HOLD (from the user and the project CLAUDE.md)
  Safety
    - "Dont break anything." Smallest change that fully solves the task. No rewrite, no framework change.
    - Preserve uncommitted work. No destructive git. Never "git add ." without reading the staged list.
    - No commit, push, merge, release or deploy without explicit approval.
    - Before each significant change: goal, scope, non-goals, acceptance, validation, risks, rollback.
  Actions
    - The model may propose. Plain code owns authorization, confirmation, running, exit codes and the log.
    - OS actions need an exact confirmation tied to one pending action, and it expires.
    - No arbitrary shell execution. Only fixed entries in ACTIONS can run.
    - Tests never really mute audio, close apps, connect devices or shut the machine down. Fakes only.
    - No destructive or disruptive action on the live Windows session during testing.
  Privacy
    - Never read or print: Data\, the log files, calendar, mail, the notes vault, the reminders and memory
      files, the ChromaDB index, the personal lines of Settings.inc.
    - New log lines hold numbers and states only. Never the user's words.
    - Never commit keys, tokens, notes, model weights, recordings, logs, local databases or caches.
  Packages and models
    - No new package, model or download before showing the smallest experiment and its disk and memory cost.
    - Never change the global site-packages. Only the private venv, and only with approval.
    - Never pick "the first model in the list". Compare and choose by result.
    - The Windows voice stays as a fallback. One microphone session at a time, always.
  Reporting
    - Report the exact commands run and what they printed. Never say a test passed unless it ran.
    - Anything that needs a real microphone, speaker, GPU or live session is "unverified" until the user

  Tools
    - Context7 for library documentation. No sub-agents unless the user asks. Planning stays on Opus.

PART C   WHAT WAS FOUND
========================================================================================================

C1. THE FIVE ROOT CAUSES
  1. Commands fall through to the chat model, and the chat model lies.
     - route() strips only the exact name "Jarvis". A misheard "Travis, ..." keeps the name in the command,
       and every command pattern is anchored on the start, so volume, mute, media, open and timer all miss.
     - reminder_cmd() knows only the words "timer" and "reminder". "Alarm" is unknown.
     - Anything unmatched goes to chat. Nothing in SYSTEM tells the model it cannot perform actions.
     - The volume pattern (about l.1394) needs digits and exact wording.
     Explains issues 8, 13, part of 10, and most likely 16 (there never was an alarm to snooze).
  2. Nothing listens while he speaks or rings.
     - wake_loop() drops the microphone whenever `busy` is held (l.2225).
     - play_samples() only checks the cancel flag, and only a click sets it.
     - alarm() listens only in the gap after the ding and the spoken line.
     Explains issues 4, 7, 9, part of 16.
  3. Every prompt carries everything.
     - system_prompt() always adds the profile (up to 2000-4000 characters), all remembered facts (up to
       2000 characters), context() (mail count, up to 6 calendar events, open apps, network, up to 12
       to-dos) and sensors(). SYSTEM says "use it when relevant". turn() always sends the last 8 messages
       and forgets only after 10 minutes.
     Explains issues 5, 11, part of 14, part of 3.
  4. Hearing runs on the weakest settings.
     - base.en, beam 1, no VAD filter, no hint that the name exists, and in the live skin: on the CPU.
     Explains issue 10 and part of 12.
  5. The GPU is not used although it works (see C2).
     Explains issue 19 and a large part of the 15-28 second replies.

3b. Autocorrect layer (standard library only, about 30 lines)
  1. Name aliases (already in 1a).
  2. Command words. In a short sentence (8 words or fewer), a word that is nearly a command word is
     corrected with difflib.get_close_matches, cutoff 0.8, against the FIXED command vocabulary only
     (volume, mute, timer, alarm, snooze, reminder, bluetooth, microphone, brightness, connect ...).
     Sentences that go to chat are never rewritten.
  3. Low confidence. Whisper gives a score per segment (avg_logprob, no_speech_prob). A COMMAND heard
     with a low score is read back ("Volume to 30?") and needs a yes. Chat questions are not checked.
  4. Device and app names keep their own fuzzy match (best_app, and the Bluetooth match in Phase 7).
  5. Ignoring slight differences (the user asked for this instead of showing the heard text):
     - Filler is removed before matching: please, could you, can you, um, uh, so, like, just, for me,
       "I want you to", "go ahead and".
     - A table of sound-alikes for command sentences only: to/too/two, for/four, eight/ate, "won" = one,
       "the value" = volume, "time are" = timer, "a larm" = alarm.
     - Small words may be missing or extra: "set volume 30", "set the volume to 30", "volume at 30" and
       "put volume on 30" are one command.
     - If a sentence matches no command exactly but is within one corrected word of exactly ONE command,
       that command is taken. Within reach of two: he asks which. A risky action (shut down, close,
       forget everything) is never reached by a correction without its normal yes.
     - The tables live in one place in jarvis.py so a new mishearing is a one-line addition.
  shortcut: no learned corrections ("when you hear X, I mean Y"). Add a small file if the fixed list is
  not enough after a week of use.

3e. Turn other sound down while he listens (issue 26; about 30 lines, no new package)

PHASE 9   ASK HIM WHAT IS WRONG (DIAGNOSIS)
--------------------------------------------------------------------------------------------------------
Fixes:  issue 21 (system logs, Task Manager information, which processes overload the system, "I could
        just ask him what the issue is")
Depends on: Phase 1 (truth rule, near-miss catch) and Phase 6a (a data block is sent only when the
question needs it). Best after Phase 2, because a diagnosis answer is longer and needs the speed.
Everything in this phase is READ-ONLY. It adds no action that changes the system.

What exists today: sensors() (l.280) gives total CPU load, temperatures from the HUD, and GPU load and
memory from nvidia-smi. Nothing per process, no logs, no disk, no network check.
The venv has NO psutil, pynvml, wmi or pywin32 (checked 2026-10-13).

9a. The design: code finds, the model words
  1. A trouble question is recognised by route(): "why is my PC slow", "what's using my CPU", "why is the
     fan loud", "what crashed", "is something wrong", "my Wi-Fi is slow", "no sound", "what's wrong".
  2. Code takes ONE snapshot (9b), on demand only. Nothing is polled in the background, so idle cost is 0.
     While it runs he says a pre-made filler ("Checking the system.") like the notes search does.
  3. Code turns the snapshot into FINDINGS with fixed rules (9d), ranked by severity.
  4. Simple questions are answered by code alone: "Chrome is using 71 percent of the CPU."
  5. For "what's wrong" the findings, never the raw data, go to the model with one instruction: explain
     these in two sentences, most serious first, invent nothing. No finding: the fixed line
     "I can't see anything wrong: CPU 12 percent, memory 48 percent, disk fine, no errors today."
  Why: a 3B model given a raw process list or raw log lines invents causes. Rules cannot.

9b. The snapshot (about 60 lines of Python plus one fixed script; about 1 to 2 seconds)
    Source                        What is read                                  Windows source
    ----------------------------  --------------------------------------------  ---------------------------
    Processes (Task Manager)      top 5 by CPU, by memory, by disk, by GPU;     performance counters
                                  names and numbers only. Many processes of      (Process, GPU Engine,
                                  one app are added up ("Chrome, 31 processes").  GPU Process Memory)
    Totals                        CPU, memory used and committed, page file      the same counters
    Disks                         free space per drive, busy time                counters, shutil
    Heat and power                temperatures, fan, battery level, charging,    sensors() today; battery
                                  battery wear, throttling                       from Windows
    Network                       connected or not, Wi-Fi signal, time to the    netsh wlan show interfaces,
                                  router and to one public address               two pings
    Devices                       devices Windows marks as faulty (count, kind)  the device list
    Windows                       time since last restart, restart pending,      Windows
                                  start-up app count
    JARVIS himself                his own problem lines (fixed texts), which     memory, not the log file
                                  parts are on the GPU, why the wake word is off

  How it is fetched, to be decided by a small timing experiment before building:
    A. One fixed PowerShell script in the Jarvis folder (diag.ps1) that prints JSON. No new package.
       Cost: PowerShell takes about a second to start. Recommended first.
    B. The psutil package (about 1 MB): faster and less code for processes, but it does not give per-process
       GPU use or the event log, so A is needed anyway. Only with approval.
  No spoken text is ever passed to the script. Its only arguments are fixed words chosen by code
  ("processes", "logs", "network"). Exit code and JSON are checked; bad output = "I couldn't read that."
  No admin rights are requested. What needs them is reported as "I can't see that without admin rights".

9c. System logs (about 40 lines)
  - Source: the Windows event log, "System" and "Application", errors and critical events of the last
    24 hours (or "since the last restart", "this week" when asked). The Security log is never read.
  - Code groups them by source and event number and counts them. A fixed table turns the known ones into
    plain words. Examples to verify one by one before building:
      unexpected shutdown or power loss      the graphics driver stopped and recovered
      blue screen                            an app crashed or stopped responding (the app's name)
      disk errors                            a Windows service stopped unexpectedly
      hardware error reported by the CPU     Windows ran low on memory
    A short list of known harmless noise is ignored.
  - An unknown event gives source, number and count only. The free text of an event is NOT sent to the
    model and not written anywhere: it can hold user names and file paths.
  - Questions answered by code: "what crashed today", "did the PC shut down badly", "any errors since
    this morning", "how often did the graphics driver crash this week".
  - Also read: Windows' reliability history (app and Windows failures per day), if the timing allows.

9d. The rules that make a finding (a fixed table; thresholds are starting values, tune after a week)
    Finding                                        Rule
    ---------------------------------------------  ------------------------------------------------------
    One app is eating the processor                one app above 50 percent CPU over the sample
    Memory is nearly full                          above 90 percent used; names the largest app
    A disk is nearly full                          below 10 percent or 10 GB free
    A disk is the bottleneck                       busy above 90 percent; names the app writing most
    The GPU is busy / its memory is full           above 90 percent; names the app (JARVIS's own model
                                                   is named as such)
    Running hot / being slowed down by heat        temperature near the limit, or throttling reported
    On battery in a power-saving mode              explains slowness on battery
    The Wi-Fi signal is weak / the router is slow  signal below 40 percent; router ping above 100 ms
    Internet down but Wi-Fi up                     router answers, public address does not
    A device has a problem                         Windows reports a faulty device
    Something crashed                              from 9c, with the count
    A restart is pending / up for many days        Windows flag; uptime above 14 days
    JARVIS is on the CPU                           from Phase 2
  Each finding is one line of numbers and names. "Why is the fan loud" = heat + top CPU app + top GPU app.

9e. What he may do about it
  - Nothing by himself. He names the cause and offers the action that already exists:
    "Chrome is using 71 percent. Want me to close it?" -> the existing close action with its yes.
  - A fixed list of Windows' own processes can never be closed, whatever is said.
  - No forced "end task", no service stop, no driver or update action. These stay with the user.
  - DECIDED by the user on 2026-10-13: he may warn without being asked, but ONLY with the pop-up line on
    the HUD, never aloud. So: a slow watch, one snapshot a minute (about 15 more lines).
      - It uses the same rules as 9d. A finding must hold for 3 checks in a row before it is shown, and
        the same finding is not shown again for 30 minutes.
      - It shows one line through the existing pop-up path (the one a muted alarm uses). No sound, no
        chime, no listening, no model call.
      - It does not run on HUD tier 3 or higher, on battery, or while a turn is busy.
      - Measure its cost first (CPU percent and milliseconds per check, per CLAUDE.md section 4). If one
        check costs more than about 1 percent of a core averaged over the minute, lengthen the interval.
      - Setting JarvisWatch = 1 (0 turns it off).

9f. Privacy
  - Process names and counts go to the LOCAL model only. Window titles are never read (they hold document
    and site names). Nothing from a snapshot is written to JARVIS's log except timings and counts.
  - He can speak app names aloud (the user agreed on 2026-10-13). In STEALTH or muted he shows the line on the HUD only, as today.

Tests (fakes: a fake snapshot, a fake script result, a fake event list)
  - Each trouble phrase routes to diagnosis; "what's using my CPU" is answered without the fake model.
  - A fake snapshot with one app at 80 percent gives exactly that finding, ranked first.
  - 31 fake processes of one app are added up under one name.

  - A fake event with free text: the text reaches neither the prompt nor the log.
